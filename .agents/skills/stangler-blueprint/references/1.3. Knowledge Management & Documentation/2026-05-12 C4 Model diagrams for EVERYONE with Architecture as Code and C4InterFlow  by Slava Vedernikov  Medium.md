This is where Architecture as Code (AaC), and specifically the C4InterFlow framework, excels. It allows for dynamic slicing and dicing of the Architecture Model based on Scope, Level of Detail, and   Diagram Type to automatically generate tailored C4 Model diagrams for every stakeholder. With C4InterFlow, you can easily create various views from different perspectives, ensuring that the right level of detail and scope is presented to the right audience, making the architecture accessible and meaningful to everyone involved. C4 Model C4 Model - Architecture Visualisation framework by Simon Brown - has gained its popularity amongst Engineers and Architects primarily for two reasons (in my view): It is focused on the Enterprise Architecture domain that is usually well understood by both technical and non-technical stakeholders i.e. Application Architecture. As per TOGAF Content Framework (see below), Application Architecture sits conveniently right between Business Architecture and Technology Architecture, so the concepts of Application Architecture can be easily linked to non-technical concepts in the Business Architecture as well as to technical  concepts in the Technology Architecture. 2. It makes it easy to communicate Application Architecture to different audiences with its 4 Levels of Detail (4 Cs): Context  (Level 1) - Software Systems and their relationships in the context of the Enterprise Container  (Level 2) - Containers  and their relationships in the context of Software System(s) Component  (Level 3) - Components  and their relationships in the context of Container(s) Code  (Level 4) - Classes  and their relationships in the context of Component(s) C4 Model — Levels of Details - c4model.com Viewpoints and Views TOGAF defines a few key concepts such as Stakeholders, Concerns, Viewpoints and Views, which when used together can help Architects to describe systems effectively for different audiences. The concepts of Viewpoints and Views that address Concerns of different Stakeholders are also relevant when using C4 Model as an Application Architecture visualisation framework. When I use C4 Model, I often think of two dimensions that help me construct relevant View(s) for a given Stakeholder  — Level of Details and Scope. Level of Details Levels of Detail are clearly defined by C4 Model. It is also easy to determine the most likely audience for views of different Levels of Detail. Scope There is another very important dimension that needs to be considered when using C4 Model to effectively document Application Architecture i.e. Scope. Defining the Scope for a particular View is basically deciding which System(s) (or Container(s), Component(s) etc.) to include in the view for a particular Stakeholder. This decision must go hand-in-hand with the decision on the Level of Details for that same view to ensure that the diagram representing the view is both useful  and readable. Your diagram will most likely be too busyand therefore unreadable  if you choose Large Scope and Low Level of Details. On the other hand, your diagram may not  be that useful  if you go for Small Scope and High Level Of Details. The problem When you take into account the Scope  and the Level of Details each time you need to communicate Application Architecture to different audiences or in different contexts (e.g. Project, Initiative, Program etc.) you will inevitably end up drawing (or codin,g when using Diagrams as Code tools) multiple diagrams. It is also guaranteed that you would have to duplicate the same structures and their relationships in those diagrams… and this is just one of many problems that you will face if you think in diagrams. I described it all in a separate article - How Architecture as Code can solve these 9 PROBLEMS with Application Architecture diagrams. Yes, Architecture as Code or to be more precise, Architecture Model as Code. I strongly believe that Architects and Engineers must stop drawing (or coding) Application Architecture diagrams if they want their documentation to last and stay relevant and useful. I explained my reasons in another article - Drawing Application Architecture Diagrams manually is “INSANE”. Architecture as Code The idea behind Architecture as Code is quite simple — express Architecture Model in code and use that model to generate diagrams for different viewpoints. There are a number of projects out there that tried to provide a Domain Specific Language (DSL) for expressing Architecture Model and some tooling for generating diagrams. Here are just a few examples: Structurizr Archinsight FINOS Labs Common Architecture Language Model (CALM) https://github.com/dwmkerr/architecture-as-code https://github.com/jsoconno/architectures When I arrived to a conclusion that Architecture Modelling is the way I want to work with Application Architecture as opposed to diagramming, I started assessing the available tools. Unfortunately, I quickly realised that all of these tools have the same flaw in common — their DSLs are built on concepts closely resembling Diagrams as Code concepts i.e. Structures (Boxes) and “hard” Relationships (Lines). So, in my view, they are not “true” modelling tools. I explained this in more details in the article My journey to C4InterFlow — Open-Source Architecture as Code Framework. Yes, I decided to build my own framework and make it open-source:) C4InterFlow — Architecture as Code framework C4InterFlow = C4 Model + Inter faces + Flow s Vision 💡 Transform the landscape of Application Architecture by bridging the gap between Architecture Model and Code. Mission 🎯 Provide a comprehensive Application Architecture framework for IT Professionals to Effortlessly express Application Architecture as Code (AaC) Use AaC to build Business Processes as Code (BPaC) Automatically generate  Application and Business Architecture diagrams  and other documentation  from AaC and BPaC Intuitively analyse Application Architecture by issuing simple queries against AaC Short story I knew that C4 Model is not an Architecture Framework, it is rather an Architecture Visualisation Framework. So, when I looked carefully at C4 Model abstractions (i.e. Software Systems, Containers, Components and Code), and I compared those to the metamodels of other frameworks like ArchiMate and TOGAF. I realised that C4 Model is “missing” a key concept that could bring it closer to an Architecture Modelling framework i.e. Interface. C4 Model abstractions — c4model.com C4 Model diagrams depict Structures (i.e. Software Systems, Containers, Components etc.) and their Relationships, but those relationships cannot be formed unless Structures expose clear Interfaces. When Interfaces are exposed by Structures then any given Interface can use  other Interfaces, and that’s how the relationships between Structures are formed. Then I thought about how any given Interface would typically use  other Interfaces, and I realised that it could be that a single Interface uses multiple other Interfaces in certain order and sometimes even conditionally. This led me to another “missing” concept i.e. Flow. Metamodel In addition to Interfaces and Flows  C4Interflow also introduces concepts like Namespace and Business Process. Namespaces can be used to logically group Software Systems (e.g. by Business Domain or Function). Business Processes can be composed of Activities performed by Actors, where each Activity can have Flows that use Interfaces. C4InterFlow Metamodel All of these concepts allow new ways of defining Scope  when deciding on what to include in the View  from a particular Viewpoint for a particular   Stakeholder. Diagram types As I said earlier C4InterFlow comes with tools like CLI that can be used to generate Architecture Diagrams. In theory any Types  of diagrams that describe Structures and their Relationships can be auto-generated, but for now C4InterFlow can generate C4, C4 Static, C4 Sequence and UML Sequence diagrams. Diagram Type adds another dimension to the previously mentioned Level of Details and Scope when it comes to deciding what View needs to be created for a particular Viewpoint. When using C4InterFlow CLI to generate diagrams you can be very specific about all three dimensions or you can omit them completely and let the framework generate diagrams for all possible combinations of all supported values of all three dimensions. Visualisation C4InterFlow CLI provides publishing command that can publish all auto-generated diagrams as a static website where anyone from your organisation can navigate Architecture Diagrams by all available Scopes, Levels of Detail, Diagram Types and Formats (including diagrams source code in PlantUML).
