As mentioned in the previous article, Structurizr brings a number of benefits over the competitors: Diagram as a code powered by robust DSL syntax to describe the elements and the relationships Ability to to!include other .dsl files into your workspaceViews with a fairly ok query langauge to include/exclude the elements in your diagram based on different criteria (tags on elements and relationships, neighbors, properties, technology type, element type, etc..)Possibility to further filter the view queries with scripts written in JS/Kotlin/GroovyWorkspaces that are top container for elements, relationships, views and styles. Then have a look at an example of structurizr workspacePurposeWith all those advantages above, I decided to solve the following:Documenting the entire architecture of your enterpriseIncrease diagram productivity for architectural decisionsThere is an argument against too many elements in Architecture Decision Records. If you have too many elements in a diagram, perhaps you trying to solve too many problems at once. For a small number of elements, a visual tool might just seem faster.However, Structurizr is valuable for its ability to define an entire enterprise architecture in a single centralized source of truth and allow you to visualize different parts of that system. Despite the apparently increased overhead to create ADR diagrams with Strucrutizr, there is a benefit. Once one of the ADR options has been accepted, you can then copy the new elements and relationships from ADR into the actual source of truth.So let’s dive into Structurizr and define our workflow for documenting the entire architectureIt’s important to take into consideration that multiple colleagues may be contributing new architecture elements and relationships in parallel.The official Strucrutizr documentation will not mandate any workflow, you have to discover it yourself. In this article, I shall describe you the one I am using.The anatomy of a workspaceWorkspace in Strucrutizr is the primary container for all the details required to draw a diagram. workspace.dsl  is basically a single file that may contain the following parts:model {} — this is where you define the C4 elements: softwareSystem, container, component, etc. Relationships are also added heremodel { archtetypes {} } — you define new element types for reuse, attach tags to them, define the default technology, etc.views {} — each diagram is defined here by using different queries to select elements defined in the model {}styles{}- customize the graphics of your diagrams. Anchor your styles two element types, tags, etc.Setting up multiple workspacesIf your enterprise is comprised by multiple domains and each divided into subdomains, then it is feasible to group the diagrams representing these domains/subdomains into workspaces.This way, each workspace will have a clear focus and the architects will have an easier time digesting your enterprise architecture one subdomain at a time.Another argument for multiple workspaces are the ADRs.Do not mix your current architecture with future proposals from ADRs. These things need to stay separate. I believe that each individual ADR should be a separate workspace.The workspace of an ADR will contain:A reference to the source of truth (includes, see below)Additional elements and relationships that ADR options requireViews to display the individual ADR optionsYou can configure Structurizr to support multiple workspaces by adding structurizr.properties  file in the root directory with the property:I doesn’t matter what number you put as long as it is greater than 1. If you have more than 2 workspaces, all will be displayed in the UI.Workspaces and sources of truthThere are different ways how you can model a source of truth in Structurizr:Workspace extensionInclude individual.dsl filesI prefer the second method because it offers me greater flexibility. With extension you inherit everything from the original workspace together with archetypes, views and styles.“Includes” however allow you to cherry pick what you regard as common for all workspaces while choosing what is individual to that specific workspace.Includes gives you total flexibility extracting different parts from your workspace.dsl into a separate source files.Directory structure of a multiple workspace setupHere is a proposed directory structure to contain your source of truth, workspaces and ADRs:You could have had only a single workspace.dsl and nothing else. But this directory structure gives you flexibility to maintain your current and future architecture.The most important parts of a workspace have been extracted into separate.dsl files and then imported into each workspace.dsl:This way, I can pull in elements and relationships from different domains by necessity into a workspace. If you don’t like the multiple includes from the source of truth (everything under /model/ directory), you can extract these!include statements into another dsl, e.g. include-all.dsl, then import only it: When your number of domains will grow, just edit the include-all.dsl to add the elements and relationships of that new domain. Views belong to workspaces We will explore views in detail in a separate article. But for now, I don’t recommend extracting the views into a separate.dsl because there is little chance for view reuse in other workspaces. Each individual view will have it’s own query syntax specific to those needs. Conclusion This article covers the minimum knowledge about directory structure and workspaces so that you can start to scale your work with C4 Diagrams in Structurizr.
